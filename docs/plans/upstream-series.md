# Plan: non-OpenStack upstream series (qemu, Linux)

## Goal

Give kerbside-patches a home for patch series against upstreams
outside OpenStack, starting with qemu and the Linux kernel. Each
series is kept with the evidence that justifies it: the guest
workload, the rig that measures it, and the results. It is kept
applying against a moving upstream, and it is either carried
downstream or submitted by mail.

The first contents come from kerbside's
`docs/plans/PLAN-spice-performance.md`, phase 2, which on
2026-09-23 produced:

- **qemu** `ui/spice-display.c` damage-path series, v2, four
  patches. qemu's non-GL SPICE path unions damage into one box,
  cuts it into 32-pixel columns and waits on a 30 ms timer. The
  series sends each damaged region whole and pushes promptly.
  - Streams went from 19 slivers of 32x360 to one 480x360
    stream.
  - Display bytes fell about 4x, and qemu CPU roughly halved.
  - Damage-to-command latency p50 fell from 14 ms to 0.2 ms.
  - It includes a unit test and worst-case benchmarks, and
    covers std-vga, qxl in VGA mode and two-head virtio.
- **Linux**: a one-line DRM core fix. `ignore_damage_clips` is
  copied into every duplicated plane state and never cleared, so
  virtio-gpu guests from 6.8 onwards report full-plane damage on
  every commit, and vmwgfx is affected in the same way. It was
  verified on 6.12.101 with a rebuilt `drm_kms_helper.ko`.
- **Rigs**: the static PID-1 KMS guests (a video-like animation
  plus clock; a two-head variant; a vesafb variant), the qemu
  and kernel build scripts, the trace and ryll-log analysis
  tools, and the results tables.

All of this currently sits in a Claude Code session scratchpad
under `/tmp`, which does not survive the session. Moving it here
is the first phase and is urgent.

## Layout, and why it is invisible to the OpenStack tooling

Every existing tool discovers projects as `./<project>/config.yaml`:

- `find . -maxdepth 2 -name config.yaml` in `assemble-source.sh`,
  `bump-source-shas.sh`, `test-patches-for-ci.sh` and
  `imagebuild.sh`;
- a `*/config.yaml` glob in `rebase-with-claude.sh`.

The patch hooks match `^_patches/`.

New series therefore live one level deeper, where none of that
can see them:

```
upstream/
  README.md            what this tree is, and how it differs from _patches/
  tools/               apply / rebase-check / build helpers (phase 2)
  qemu/
    config.yaml        repo, branch, base_sha, disposition (carry | submit)
    series/            git format-patch output, cover letter included
    rig/               guest sources, run scripts, analysis tools
    results/           summary tables (not raw captures)
  linux/
    config.yaml
    series/
    rig/
    results/
```

Why this layout:

- **Why not `_patches/` plus `ORDER` files.** A mailed series
  is reviewed and resent as a unit (v1, v2 and so on, with a
  cover letter), and `git am` wants it as `format-patch` output.
  Splitting it into numbered `patchNNN` files would lose that
  shape and gain nothing: none of the OpenStack tooling should
  touch these series anyway.
- **A new `release` value was considered and rejected.** It
  would hide the series from `assemble-source.sh` but not from
  `bump-source-shas.sh` or `test-patches-for-ci.sh`, which do not
  filter on release. That would mean editing every tool, and
  every tool added later would have to remember the exception.
- **Raw captures stay out of git.** They run to hundreds of MB.
  Summary tables go in `results/`. Raw data is regenerated by
  the rig.

## Phase 1 --- import

Copy from the session scratchpad
(`.../scratchpad/qemu-damage/` and `.../scratchpad/kernel-damage/`):

- qemu: `patches-v2/` into `upstream/qemu/series/v2/`. v1
  (`patches/`) is kept as `series/v1/` for history. It also gets
  the guest sources, `tools/`, `bench/bench.c`, and `summary.md`
  plus the v2 results as `results/`.
- linux: the drafted patch into `upstream/linux/series/v1/`,
  plus `run-trace.sh`, the guest sources and the results.
- The scratch clones' base SHAs go into each `config.yaml`: qemu
  30e8a06b64, and linux drm-misc-next 2302669bb4b5 (the patch
  also applies to master, drm-misc-fixes and v6.12.101).
- Built artefacts are not imported: initramfs images, kernel
  modules, qemu builds, the `sysroot/` of extracted `.deb`s.
  Each rig gets a build script instead, if it lacks one.

Checks: shellcheck on the imported scripts (the repo lints
`tools/` and `_build/`, so extend it to `upstream/`), and each
series `git am`s cleanly onto its recorded base SHA.

## Phase 2 --- keep them applying

- **`upstream/tools/apply.sh <project> [--series vN]`.** A
  shallow fetch of `base_sha`, then `git am` the series. With
  `--onto <ref>`, try the latest upstream instead and report the
  result.
- **A scheduled workflow**, separate from
  `daily-rebase-checks.yml`. It runs the `--onto` check weekly
  against qemu master and drm-misc-next or torvalds master. On
  failure it opens (or updates) an issue rather than attempting
  a Claude-driven rebase.
  - Upstream submission is the goal, so a rebase is a new
    version of the series, and a human decides when to cut it.
  - Following the fleet convention, the workflow calls a script
    in `upstream/tools/` rather than carrying logic inline.
- **Watch for the fix landing upstream.** For linux, the check
  also looks for the fix on the target branch, so we notice when
  the upstream fix makes the series redundant.

## Phase 3 --- build and measure in CI

This phase builds the patched qemu (and the kernel module) and
runs the rig on a runner with `/dev/kvm`, comparing stock with
patched. Open points to settle when it is planned:

- **Runner size.** Unsized shakenfist VM jobs default to xs (one
  core, 2 GB), which is too small for a qemu build. The runner
  label must name its size.
- **Build dependencies.** Can the runner `apt install` them, or
  does it need the extracted-deb sysroot approach the prototype
  used without sudo?
- **The Ryll client.** The rig needs Ryll built in Docker. Ryll
  issues #398-#400 limit what it can measure; H.264 in
  particular does not decode today.

## Phase 4 --- submission path

- **The kernel patch.**
  - The kernel accepts AI-assisted patches under
    `Documentation/process/coding-assistants.rst`: an
    `Assisted-by:` tag, and the human's own `Signed-off-by`,
    which only Michael can add.
  - Recipients are recorded from `get_maintainer.pl`
    (dri-devel, the DRM misc maintainers, the Fixes author,
    vmwgfx and virtio-gpu people).
  - drm-misc-next already fixes virtio-gpu (a9cc9905ddb7 on
    top of 730f8554f35c), without a stable tag. Maintainers may
    prefer a vmwgfx-only patch plus a stable backport request,
    so the cover note says so.
  - Document a b4 / `git send-email` checklist in
    `upstream/README.md`.
- **qemu: carry downstream, do not submit.**
  - qemu's `docs/devel/code-provenance.rst` declines
    contributions believed to include or derive from
    AI-generated content, and names Claude.
  - Decided 2026-09-24: carry the series downstream while
    Michael gets familiar with qemu. He can rewrite it by hand
    later.
  - Whether that is ever worth doing depends on kerbside's
    son-of-SPICE spike, a Rust SPICE server on qemu's D-Bus
    display. That would bypass `ui/spice-display.c` entirely,
    though Nova and oVirt deployments would still run in-qemu
    SPICE.
  - `config.yaml` records `disposition: carry`.

## Phase 5 --- push audit

This repository has no `PUSH-AUDIT.md` yet, so this phase says
that and records what was done instead: a review of the
accumulated diff of phases 1-4 for secrets, stray artefacts,
scripts that assume the scratchpad paths, and licensing of the
imported rig code. The merge commit of each phase is recorded in
the Status table as it lands.

## Decided

- The series live in kerbside-patches (Michael, 2026-09-23), not
  in a new repository or in kerbside itself. They go under
  `upstream/`, out of reach of the OpenStack tooling.
- qemu is carried downstream, not submitted (2026-09-24).
